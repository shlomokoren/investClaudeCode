# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pip install -r requirements.txt
cp .env.example .env          # DATABASE_URL, SECRET_KEY, GOOGLE_CLIENT_ID/SECRET (see below)
python init_db.py             # create the tables and seed them from config.json
python init_db.py --show      # dump global config + every user and their watch list
python app.py                 # runs on 127.0.0.1:5000 by default (HOST/PORT/DEBUG env vars)
```

Required env vars: `DATABASE_URL` and `SECRET_KEY` (app refuses to start without the
latter), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` for real login. For local work
without Google credentials, `DEV_LOGIN_EMAIL=you@example.com` adds a one-click login
bypass to `/login` — double-gated on `DEBUG=true`, so it's inert in any deployment.

Docker:
```bash
docker build -t investclaudecode:dev01 .
docker run -it --rm -p 5000:5000 --env-file .env -d --name invest investclaudecode:dev01
```

There are no automated tests or linters configured in this repo currently.

`AGENTS.md` is a condensed duplicate of this file for non-Claude agents — if you change architecture-relevant facts here (env vars, file responsibilities, deployment contract), mirror the change there too.

## Architecture

Multi-user Flask app with two feature areas wired together as blueprints, sharing one login gate and one page layout. Every user has their own watch list.

- **`app.py`** — creates the `Flask` app, sets `app.debug` from `DEBUG` *before* `auth.init_app()` (cookie flags depend on it), requires `SECRET_KEY` (no fallback — a fixed default would let anyone forge a session), registers the two blueprints and a public `/healthz` used by deployment probes since `/` now redirects to login. `__version__` here is the single source of truth for the release version — returned by `/healthz` and shown on the Help page (MAJOR = deploy needs manual work, MINOR = new feature, PATCH = fixes). It must match the top dated section of `CHANGELOG.md`. `.github/workflows/release.yml` runs on every push to `main`, reads `__version__`, and — if no release for that version exists yet — tags the commit `vX.Y.Z` and publishes a GitHub Release whose notes are the matching `## [X.Y.Z]` block of `CHANGELOG.md` (falling back to auto-generated notes if that block is absent). So a release is cut by moving the `CHANGELOG.md` `[Unreleased]` bullets under a dated heading, bumping `__version__` to match, and merging `dev` → `main`; nothing is tagged by hand.
- **`auth.py`** — Google OIDC via Authlib. `init_app()` installs a global `before_request` login gate, so **new routes are protected by default**; anything public must be named in `PUBLIC_ENDPOINTS`. Also installs `_reject_cross_origin_writes` (cheap CSRF guard: non-GET with a foreign `Origin` → 403) and a context processor exposing `current_user` to templates. Sessions are signed cookies (permanent, 30 days, `HttpOnly`/`SameSite=Lax`/`Secure` unless debugging) — no server-side store, so they work across gunicorn workers. Cookie flags are **assigned, not `setdefault()`**: Flask ships those keys with weaker defaults already present, so `setdefault` would silently no-op. Login upserts `app_user` keyed on the verified email, then `db.ensure_user_defaults()` gives new users an empty list. `/auth/dev-login` is a local bypass gated on `DEV_LOGIN_EMAIL` *and* `current_app.debug`; `dev_login_email(app=None)` takes an explicit app because `init_app()` runs outside any app context.
- **`db.py`** — Postgres (Neon) access layer. `DATABASE_URL` is read from the environment or a local `.env` (loaded via `python-dotenv`); there is no hardcoded fallback, so a missing value raises at first DB use rather than silently degrading. Three tables: `app_config(key, value jsonb, updated_at)` for global settings, `app_user(id, email unique, provider, provider_sub, name, created_at, last_login_at)`, and `user_config(user_id -> app_user ON DELETE CASCADE, key, value jsonb, updated_at)` keyed `(user_id, key)`. `upsert_user()` matches on **email**, not `provider_sub`, so `init_db.py` can pre-seed an account before its first login and the real login updates that row in place. A lazily-created `psycopg_pool.ConnectionPool` (`min_size=0`, `max_size=4`) is per-process, so each gunicorn worker holds its own; `close_pool()` exists for scripts.
- **`init_db.py`** — one-off bootstrap: `ensure_schema()`, seed global keys from `config.json`, then seed `owner_email`'s watch list (`--force` to overwrite, `--show` to dump config + users + lists, `--seed-user EMAIL` to target another account). It reads the live `app_config` ticker list *before* overwriting globals, so UI edits aren't lost to a stale `config.json`. `config.json` is *only* a seed file — nothing reads it at request time.
- **`symbols.py`** — global settings (`load_global_config()`) are cached in-process for `CACHE_TTL_SECONDS` (60) since they're identical for everyone. **Per-user config is deliberately never cached** — a shared cache would serve one user's ticker list to another, and it's a single primary-key lookup on `user_config`. `load_config(user_id)` layers the user's rows over the globals but forces `default_stocks` to `[]` first, so a user who has added nothing gets an empty list rather than the global seed list. `load_symbols(user_id)`, `add_symbol(user_id, symbol)`, and `remove_symbol(user_id, symbol)` are all user-scoped. Both blueprints pass the signed-in user's list into their template as `symbols`, which renders a row of clickable ticker chips on both pages (`public/js/price.js` and `public/js/dashboard.js` each wire up click handling for their own page's chips independently — there's no shared JS between the two). The price page wraps each chip in `.chip-wrap` with a `.chip-remove` × button and adds an *Add symbol* form; the financials page renders bare `.chip` buttons, so keep `.chip` styling changes safe for both.
- **`templates/base.html`** — shared layout (tab nav + `<head>`/Chart.js include). The nav renders tabs, the signed-in email, and a POST sign-out form only when `current_user` is set, so `login.html` can extend the same base without them. `price.html`, `financials.html`, `status.html`, `events.html`, `news.html`, and `login.html` extend it and fill the `content`/`scripts` blocks. All styling lives in the single `public/css/style.css` (no per-page stylesheets).
- **`blueprints/price.py`** — also owns the ticker-list editor used by the Price tab: `POST /api/symbols` and `DELETE /api/symbols/<symbol>`, both scoped to `current_user_id()`. Adds are validated in three steps (regex `SYMBOL_RE`, duplicate check, then `symbol_exists()` which asks yfinance for 5 days of history) so typos never reach the database. Both endpoints return the full updated list, which `price.js` re-renders chips from. The add/remove SQL in `db.py` is a single atomic statement over the jsonb array rather than a read-modify-write, so concurrent edits can't clobber each other. In `price.js`, `setTickers()` calls `syncChipState()` itself — assigning `input.value` doesn't fire the `input` event, so without that a programmatic change leaves chips looking inactive. `fetch_stock()` pulls extra calendar padding (`display_days + SMA_WINDOW*1.5 + 30`) before the requested display range so the 150-day SMA is fully defined from day one of the visible window, then trims back to the display range before returning JSON.
- **`blueprints/financials.py`** — pulls income statement + cash flow statement via `yfinance`. Row labels aren't consistent across tickers/yfinance versions, so `METRIC_LABELS`/`FREE_CASH_FLOW_LABELS`/etc. list fallback label names, and `_extract_row()` tries them in order. Free Cash Flow is computed as Operating Cash Flow + Capex when yfinance doesn't report it directly (capex is stored negative). Results are cached in an in-memory dict (`_cache`) keyed by `(symbol, period)` for 24 hours — this cache is per-process and resets on restart/redeploy. Every successful `/api/financials` request (cache hit included, but never an error) records the ticker via `symbols.set_financials_symbol()` (`db.FINANCIALS_SYMBOL_KEY`, a plain string not a list); `index()` reopens the page on that symbol (`initial_symbol`), falling back to the first watch-list ticker then `NVDA`, so a refresh keeps the last-viewed company.
- **`blueprints/status.py`** — the Portfolio tab. `/api/status` returns each watch-list symbol with name/previous-close/current-price/daily-change (one `yf.Ticker().info` call per symbol) plus the user's saved position; `/api/status/position` (POST) persists a per-symbol share count via `symbols.set_position()`. `status.js` renders the sortable table, a total-value line, and a Chart.js allocation pie (positions of 0 are excluded from the pie). A multi-select chip row filters the table/total/pie; the selection is persisted per-user exactly like the News tab — `POST /api/status/symbols/<symbol>` `{selected}` → `portfolio_hidden` jsonb list (opt-outs, via `symbols.set_portfolio_symbol_hidden()` / `db.PORTFOLIO_HIDDEN_KEY`), rendered back onto the chips' `active` class, and cleared by `remove_symbol()`.
- **`blueprints/events.py`** — the Events tab: each watch-list symbol's next earnings date and dividend schedule. `/api/events` does three yfinance reads per symbol — `Ticker.calendar` (earnings / ex-dividend / pay dates), `Ticker.info` (names, fallback dates, `dividendRate`), `Ticker.dividends` (last paid amount + payout frequency inferred from the median gap between recent payments). `_as_date()` normalises the assorted shapes yfinance returns (date, Timestamp, epoch seconds, or a `[start, end]` list — earnings is often a range, and a mismatched start/end is surfaced as an "est." flag). Per-symbol results are cached in `_cache` for 6 hours (per-process, resets on restart/redeploy); a fetch failure caches a stub row rather than failing the whole page. `events.js` renders the sortable table client-side, default-sorted by soonest upcoming event. A multi-select chip row filters the table, persisted per-user like the News/Portfolio tabs (`POST /api/events/symbols/<symbol>` `{selected}` → `events_hidden` jsonb list via `symbols.set_events_symbol_hidden()` / `db.EVENTS_HIDDEN_KEY`; `/api/events` takes an optional `?symbols=` and otherwise defaults to the watch list minus that list).
- **`blueprints/news.py`** — the News tab: recent Yahoo Finance headlines for the watch-list symbols, via `yfinance.Ticker.news` (chosen over a keyed news API to avoid threading a new secret through every deployment config). `/api/news?symbols=A,B&days=2` merges per-symbol news, dedupes by item id, filters to the last `days` (default 2, clamped 1–30), and sorts newest-first. `Ticker.news` is fetched whole and cached per-symbol in `_cache` for 20 minutes, so changing the `days` window never refetches. `_normalise()` reads both the pre-1.x flat item shape and the current nested `content` dict (title/summary/pubDate/provider/canonicalUrl/thumbnail). `symbols` is intersected with the user's actual watch list before fetching. `news.js` mirrors the Price tab's multi-select chips plus a look-back `<select>`, and renders a scrollable feed (`.news-feed`, `max-height` + `overflow-y`). The chip selection is persisted: `POST /api/news/symbols/<symbol>` with `{selected: bool}` writes to the `news_hidden` per-user jsonb list (via `symbols.set_news_symbol_hidden()` / `db.NEWS_HIDDEN_KEY`, reusing `add_user_symbol`/`remove_user_symbol`). Like `disabled_stocks`, the list stores the *opt-outs* so a newly-added watch-list symbol appears in news by default; `remove_symbol()` also clears a symbol's `news_hidden` entry. The template renders each chip `active` unless the symbol is in `hidden`, so the choice survives a refresh or reopening the tab.

### Deployment targets

All deployment configs need `DATABASE_URL`, `SECRET_KEY`, `GOOGLE_CLIENT_ID`, and `GOOGLE_CLIENT_SECRET` in the environment, and all probe `/healthz` (not `/`, which redirects to login). Each host's `https://HOST/auth/google/callback` must also be registered as an authorized redirect URI in the Google OAuth client.
- `Procfile` (Heroku-style, `gunicorn app:app`). Plain sync workers over a blocking network call per ticker fetch — bump `--workers`/add `--threads` before relying on it under real concurrent load.
- `k8s/` manifests (namespace/secret/deployment/service/ingress/OpenShift route) — all four values come from the `invest-app-db` secret via `secretKeyRef`; the old ConfigMap that mounted `config.json` is gone
- `Dockerfile` (copies `app.py`, `auth.py`, `symbols.py`, `db.py`, `init_db.py`, `config.json`, `blueprints/`, `templates/`, `public/`; runs `python app.py`, not gunicorn)
- **Vercel** (`vercel.json`) — Python runtime, zero-config: Vercel detects the top-level `app` Flask instance in `app.py` and runs the whole app as one serverless function (Fluid Compute), so no route-by-route restructuring is needed. `vercel.json` sets `maxDuration: 60` for `app.py` since sequential per-ticker yfinance calls can take a few seconds. Because instance count can scale far more elastically than a fixed number of gunicorn workers, `DATABASE_URL` should point at Neon's **pooled** connection string (`-pooler` host) when deployed here, to avoid exhausting Postgres connections under concurrent invocations — the direct string works locally and under a fixed worker pool. In-memory caches (`symbols.py`'s 60s global-config cache, `blueprints/financials.py`'s 24h cache) still work but are only as durable as the underlying function instance — expect more cache misses than under a single long-lived process. `DEBUG` must stay unset/false, same as any other deployment.

Static assets live in `public/`, not `static/` — `app.py` sets `static_folder="public", static_url_path=""` so Flask serves them at the site root (`/css/style.css`, not `/static/css/style.css`). On Vercel, files under `public/**` are instead served directly by its CDN rather than passing through the function, which is why the folder has to be named exactly `public` there; the matching Flask config keeps local behavior identical without any template changes (`url_for('static', ...)` still resolves correctly).

When adding new top-level modules or directories that the app imports at runtime, update the `COPY` lines in `Dockerfile` accordingly.
